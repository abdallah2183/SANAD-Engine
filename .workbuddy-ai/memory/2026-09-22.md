## Notes / gotchas learned
- **`rc=3` from a test binary = MSVC `abort()`** (debug iterator/`_STL_VERIFY`
  or an unhandled abort), NOT a framework failure — the framework returns only
  0/1. `std::cout << std::unitbuf` in `Tests/TestFramework.cpp` means every line
  is flushed, so a missing `[ OK ]` after `[ RUN ]` is a real hard death.
- **Test binaries take a name filter as `argv[1]`** (`AudioTests <substr>`) —
  the reliable way to bisect a crashing suite. Use it.
- Run the whole sweep **in the background with a per-suite `timeout`**; a
  foreground sweep can exceed the shell timeout and get SIGTERM'd mid-way
  (loses the log tail).
- `Tests/CMakeLists.txt` still has no unregistered test files — keep it that way.

## Toolchain fix — full build was red from a machine-level NuGet break
- **Symptom:** `dotnet build` (the `NFCSharpSandbox` CMake custom target) aborted
  with `NuGet.targets(782,5): error : Value cannot be null. (Parameter 'path1')`,
  making the **whole** build red while every C++ TU compiled fine.
- **Root cause (proven):** the agent shell env is missing the standard Windows
  variables — `APPDATA`, `ProgramData`, `ALLUSERSPROFILE`, `ProgramFiles`,
  `ProgramFiles(x86)`, `CommonProgramFiles`, `CommonProgramFiles(x86)` are unset.
  NuGet derives its machine-wide config paths from them → `null` →
  `Path.Combine(null, …)` throws in `GetRestoreSettingsTask`'s static ctor.
  Reproduced on a throwaway `net10.0` project **outside the repo** and with the
  sandbox disabled → machine-level, not repo code, not any model's fault.
  (`dotnet --version` 10.0.300; net10.0 ref pack 10.0.8; NuGet configs all valid.)
  Debug path: `dotnet build -v diag` → stack `GetRestoreSettingsTask.<>c.<.cctor>`
  → `RestoreSettingsUtils.ReadSettings` → `Path.Combine`; then probe child env
  with the managed python to see which vars are `None`.
- **Fix:** `.workbuddy-ai/nfb.sh` now restores those seven vars via `env` (needed
  because `ProgramFiles(x86)` is not a legal bash identifier) before
  `cmake --build`, with `MSYS_NO_PATHCONV=1` so the values keep their backslashes.
  Proof: deleted `NFGameScript.dll`/`.runtimeconfig.json` to force the target →
  `Build succeeded, 0 errors, rc=0`.
- **Note for future sessions:** if `dotnet` ever fails again with a null-path
  error, check `nfb.sh` still has the env-restore block — and remember
  `ninja` will *skip* the C# target when the `.cs` is older than the DLL, so
  force it by deleting the artifact when you need to prove it.
- Also: `NFSandbox.cs` mtime moved between checks — a teammate was rewriting it
  mid-flight; do not read file mtimes as stable during a parallel run.
