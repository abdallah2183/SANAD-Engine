## 1. `scenes_equal_structure` compared the wrong pair (finding 2026-10-02)
- `Editor/src/PlayMode.cpp` indexed the saved scene by name into a **single**
  slot. Names are not unique: `Runtime.cpp` synthesizes one from the entity's
  KIND for every entity with no `Name:` line, so a scene with two meshes has two
  entities called `"Mesh"`. Every live `"Mesh"` was compared against the LAST
  saved one, so a correctly round-tripped scene reported `transform values
  differ for 'Mesh'` and the editor exited 1.
- **Fix:** index into a `vector` per name and pair the Nth of a name with the
  Nth. That is the right pairing — both lists come from the same file order, and
  a re-save cannot reorder what the loader wrote in order. A cursor map, not
  erase-from-front, so a 2000-entity scene stays linear.
- `#<id>` stays as the fallback for hand-built scenes; the editor path can never
  hit it because Runtime names every entity on load.

# 2026-10-03 (later) — the scene's audio environment (G5 step 2)

Both are real features but neither lands safely in one push.

Full build exit 0. Sweep **26 suites, 1780 passed / 0 failed / 2 skipped**
(was 1775; +5). Editor acceptance windowed 125f: exit 0, `automation=OK`,
`cube lit pixels = 229149` (unchanged — no GPU code was touched).

## What landed

`.nfscene` gained three ENTITY component lines — `ReverbZone:`, `Music:`,
`Ambience:` — plus the runtime that builds them into the live `AudioScene`.

- **Entity components, not scene-level records.** Scene v1 expects `---`
  immediately after `entity_count`, so a global list would be a format
  migration. Placing the echo by placing an object is also what an author
  wants, and a reverb zone's position IS the entity's transform.
- **`Engine/Audio/include/NF/Audio/Components.hpp`** — `ReverbZoneComponent`,
  `MusicComponent`, `AmbienceComponent`. They live beside `AudioComponent`
  because `RuntimeSceneTypes.hpp` is deliberately flat floats (the editor and
  the tools include it) and `AudioBuffer` must not leak into it.
- **`AmbienceComponent` has no volume field on purpose.** `set_ambience` takes
  a buffer and a fade and nothing else, so a volume would be parsed, saved and
  round-tripped while never reaching the mixer — the "field with no reader"
  defect. Ambience level is the `ambience` bus slider's job.
- **`Runtime::build_scene_audio()`**, called from `adopt_scene` beside
  `build_scene_particles` / `build_scene_cloths`. It REPLACES the previous
  scene's environment: zones cleared, and a theme/bed the new scene does not
  name is stopped. Deliberately the opposite of the post-process rule ("absent
  means unchanged") — those are renderer settings a caller may have configured
  directly; these are per-scene artefacts, and a level change must not leave the
  old cave echoing under the new one.
- **Runtime-owned sample buffers.** `MusicSystem` holds the buffer pointer
  across frames and the editor creates entities between them, so pointing at a
  component's `owned_buffer` would dangle on a world reallocation. The samples
  are copied into `m_scene_music_buffer` / `m_scene_ambience_buffer`.
- **`resolve_scene_audio` refactored** to one `decode_scene_audio` helper shared
  by all three, so they cannot drift in how a missing/undecodable file is
  reported. `what = "Audio"` reproduces the original message byte for byte.
- ReverbZone validation: a non-positive radius is REFUSED with a warning (it
  would be indistinguishable from a deliberate "no reverb here"); an inner
  radius past the outer one is CLAMPED (a tunable that got dragged, and the
  falloff must not invert).

## Tests — 5 new, `Tests/RuntimeTests/test_runtime_scene_audio.cpp`
Round trip of all three lines; a scene without them writes no line AND still
re-serialises to the same bytes; the zero-radius refusal and the inner-radius

scene swap that clears zones, stops music and drops the bed.

**Rule 0:** removing the `build_scene_audio()` call from `adopt_scene` fails

# 2026-10-03 (third) — the editor UI for the audio environment

The named remaining half from the previous push. Full build exit 0. Sweep

(unchanged), 0 validation errors, 0 RHI leaks. `audit_imgui_ids.py`: 6
candidates, all pre-existing. UITests 42/42 (the 17 new keys are duplicate-free).

## What landed

Three inspector sections, three undo/redo commands, three validated factories,
three `EditorApp` setters, 17 Arabic keys.

- **`SetReverbZoneCommand` / `SetMusicCommand` / `SetAmbienceCommand`** follow
  `SetPostProcessCommand` exactly: undo of the edit that FIRST created the
  component removes it, so a scene that never had the line round-trips to a file
  with no line.
- **The inspector cache holds the reverb zone as the component** (six floats and
  a bool — a mirror struct would be pure translation) but holds only the fields
  the widget shows for music/ambience. Those components own DECODED SAMPLES, and
  copying megabytes into a per-frame cache for a value the widget never shows is
  the wrong trade.
- **Music and ambience are deliberately NOT in the Add-component menu.** Both
  need a buffer path, and `set_music`/`set_ambience` refuse an empty one, so the
  menu entry could only ever fail. Their sections' EMPTY state carries the path
  field and the add button instead.
- **`EditorApp::set_music`/`set_ambience` resolve the path through the VFS**,
  mirroring `set_audio_buffer`, so an authored track is audible immediately
  rather than after a save and reload. A path nothing can decode is REFUSED and
  the live component is left alone — the author is standing right there.
- **The samples are carried over when the path did not change.** The command
  holds both states, so re-resolving on every Apply would re-read the file; the
  carry-over also means an edit cannot silence a track that is already decoded.
- Validation mirrors the scene loader's bounds on purpose (radius > 0,
  inner <= radius, wet in [0,1], non-negative times, volume in [0,1]): a value
  the editor accepts and the loader then drops would make the same scene load
  differently depending on how it was authored. A zero radius is REFUSED here
  rather than clamped, because the loader drops such a line.

## Tests — 4 new, `Tests/EditorTests/test_audio_env_editor.cpp`

a dead entity) and one `EditorApp` case that proves the path resolves through the

**Rule 0:** removing the sample carry-over fails
`editor_set_music_resolves_the_path_and_keeps_the_samples` (260/1). The test

# 2026-10-03 (fourth) — lens effects: the first §206 stage added since Phase 27

Full build exit 0. Sweep **26 suites, 1789 passed / 0 failed / 2 skipped**
(was 1784; +5). Editor acceptance windowed 125f: exit 0, `automation=OK`,
`cube lit pixels = 229149` (unchanged — the stage is exactly identity when off),
0 validation errors, 0 RHI leaks. `audit_imgui_ids.py`: 6 candidates, all
pre-existing. UITests 42/42 (3 new keys).

## Why this and not DOF
DOF is the bigger prize and it is now UNBLOCKED (the depth target has `Sampled`
usage, and `lighting.frag` already reconstructs world position from
`frame.invViewProj`, so a DOF pass can copy the lighting pass's binding shape).
It is also a much larger change — a new pass, pipeline, render pass, graph
texture and descriptor layout, plus the question of whether bloom should read
the DOF'd image. Lens effects is the same §206 stack item at a fraction of the
surface, and it lands complete (renderer + scene data + editor + tests) rather
than half-landed. DOF stays the named next rendering push, with the architecture
recorded in MEMORY.md so it is not re-derived.

## What landed

- **`LensParams`** in `PostFxParams`: `enabled`, `distortion` (signed barrel /
  pincushion coefficient on r²), `chromatic_aberration` (red-out/blue-in radial
  split as a fraction of r). Both neutrals are EXACTLY identity.
- **A UV-space warp, not a filter.** The HDR is fetched at the warped
  coordinate, so the stage needs no neighbourhood — which is what makes it
  exactly mirrorable on the CPU and cheap on the GPU. Green is never displaced,
  so a neutral grey pixel stays neutral and only a real colour edge fringes.
- **`lens_sample_uv()` is a SEPARATE CPU mirror from `apply_post_chain`.**
  `apply_post_chain` receives an already-fetched colour and has no coordinate to
  warp, so mirroring the lens inside it was impossible; keeping them apart is
  what lets both be exact, and it is documented on both.
- **The shader has no enabled flag.** `enabled` is folded into the two
  coefficients at push time — the same thing `bloom_on` does for the intensity —
  and the CPU mirror folds it identically, or the two would compare different
  images.
- **Distortion composes before chroma**, and the order is pinned by a test that
  computes BOTH orders and asserts they differ.
- Scene data: `lens=` / `lens_distortion=` / `lens_chroma=` on the
  `PostProcess:` line (bounds -0.5..0.5 and 0..0.1, matching the editor's);
  `PostProcessComponent` fields; `extract_post_process` pushes them. Editor:
  a Lens block in the Inspector (checkbox + two sliders), factory bounds,
  3 Arabic keys.

## The trap this turn, and it was a good one
Growing the tonemap push block 16 → 20 floats broke **19 unrelated RHITests**,
all with `rhi::validation_error_count() != 0`. Cause:
`PipelineDesc::push_constant_size` is not documentation — it becomes the
Vulkan push range, and the tonemap pipelines declared 64 bytes. The failing
tests were shadow/transparency/sky tests that have nothing to do with the post
stack; the only signal was the validation counter. **There are TWO tonemap
pipelines** (offscreen and present) and both had to change. Check
`push_constant_size` whenever a push block changes.

## Tests — 5 new
`post_stack_lens_neutral_is_identity` (defaults AND unchecked-with-values),
`..._distortion_moves_the_edges_out` (centre fixed, both signs),
`..._chroma_splits_red_out_and_blue_in`, `..._applies_distortion_before_chroma`,
and a GPU case `post_stack_lens_changes_the_rendered_image` (enabled-but-neutral
is pixel-IDENTICAL; distortion moves >1/8 of the frame; the centre survives; the
corner moves). Plus the neutral-defaults and round-trip/push/editor tests
extended in place.

**Rule 0:** swapping the composition order in the mirror fails
`post_stack_lens_applies_distortion_before_chroma` (245/1).

# 2026-10-03 (fifth) — depth of field: the last big §206 stage

Full build exit 0. Sweep **26 suites, 1792 passed / 0 failed / 2 skipped**
(was 1789; +3). Editor acceptance windowed 125f: exit 0, `automation=OK`,
`cube lit pixels = 229149` (unchanged — the stage is exactly identity when off),
0 validation errors, 0 RHI leaks. `audit_imgui_ids.py`: 6 candidates, all
pre-existing. UITests 42/42 (4 new keys).

## Architecture: inside the tonemap pass, not a new pass
Phase 27 deferred DOF because it "wants a physical lens model and the depth
target read back as a texture". Both were available: the depth target already
carries `Sampled` usage, and the frame block already holds the
inverse-view-projection the lighting pass uses to reconstruct world positions.

Two ways to build it. A separate pass (its own pipeline, render pass, graph
texture, descriptor layout) — more machinery, plus the question of whether the
bloom prefilter should then read the DOF'd image. Or **inside the tonemap pass**
— the depth target and the frame block simply join the tonemap descriptor
layout, and the stage sits in the existing chain. Chose the second: no new
pipeline, render pass, graph texture or framebuffer, and no second HDR target.

## What landed

- **`DofParams{enabled, focus_distance, focus_range, max_radius}`** in
  `PostFxParams`. A linear circle-of-confusion ramp, not a thin-lens model: the
  two things an author sets are where it is sharp and how far the blur takes to
  reach full width.
- **`max_radius` 0 is the off switch.** `enabled` folds into it at push time (the
  `bloom_on` pattern), so the shader has no flag, an off stage costs one compare,
  and the golden pixels are untouched.
- **A golden-angle disc gather**, taps weighted by their OWN confusion clamped to
  the centre's — a centre-only weighting smears a sharp foreground onto a blurred
  background at every silhouette edge.
- **`dof_coc()` is the CPU mirror** (the part with the physics in it). The gather
  needs a whole image, so it is covered by a GPU test — the same split the bloom
  chain uses.
- Scene data (`dof=`, `dof_focus=`, `dof_range=`, `dof_radius=`),
  `PostProcessComponent` fields, `extract_post_process`, an Inspector block,
  4 Arabic keys.

## The traps this turn

1. **The tonemap descriptor layout grew 5 → 7** (frame block + depth). It is
   shared by FOUR pipelines and written at TWO sites. The present site's loop
   wrote every binding as a SampledImage — but binding 5 is a UNIFORM BUFFER, so
   it had to be special-cased. An image view in a uniform-buffer binding is a
   validation error, not a harmless substitution.
2. **My first `dof_coc` test was wrong, not the code.** I assumed `focus_range`
   was the half-width of a zero-confusion band; the ramp actually saturates AT
   `focus_distance +/- focus_range`, so those two depths are fully confused. The
   code was right and the doc was vague — fixed the doc and the test, and the
   semantics are now stated in three places.
3. `DofParams` had to be declared BEFORE `PostFxParams` (it is a member), and
   the tonemap pass had to DECLARE the depth handle as a read or the graph would
   never transition it into a sampled layout.

## Tests — 3 new
`post_stack_dof_coc_is_zero_inside_the_focus_band` (symmetric, linear, clamped),
`post_stack_dof_off_is_exactly_zero_confusion` (disabled, zero radius, zero
range), and a GPU case `post_stack_dof_changes_the_rendered_image` with three
deterministic states off an empty scene: enabled-with-zero-radius is
pixel-identical, **focused on the far plane is pixel-identical** (the half that
proves the blur is depth driven), and focused near visibly changes the frame.

**Rule 0:** making the circle of confusion ignore depth fails
`post_stack_dof_changes_the_rendered_image` on exactly the "focused far is
identical" assertion (248/1).

## §206 status after this
Implemented: exposure, colour grading, bloom, DOF, lens effects, tonemapping,
sharpening, saturation, vignette. **Only motion blur remains deferred**, and it
is still genuinely blocked: the deferred path writes no velocity buffer.

# 2026-10-03 (sixth) — motion blur: §206 COMPLETE

Full build exit 0. Sweep **26 suites, 1796 passed / 0 failed / 2 skipped**
(was 1792; +4). Editor acceptance windowed 125f: exit 0, `automation=OK`,
`cube lit pixels = 229149` (unchanged — the stage is exactly identity when off),
0 validation errors, 0 RHI leaks. `audit_imgui_ids.py`: 6 candidates, all
pre-existing. UITests 42/42 (2 new keys).

## The blocker, solved without a velocity buffer
Motion blur was the last deferred §206 stage and the note said it "wants a
velocity buffer the deferred path does not write". It does not have to: the
world position can be reconstructed from the depth target (the DOF stage already
does exactly that) and projected with the PREVIOUS frame's view-projection. That
is the classic reprojection, and it needs no extra gbuffer attachment and no
per-object previous-model matrix — which also matters because a per-object
`prev_model` would have pushed the 128-byte vertex push block past the Vulkan
minimum guarantee.

The honest scope this buys: **camera motion blur**. A surface's own movement is
not in the depth buffer, so a fast object under a still camera does not smear.
Documented in three places rather than glossed over.

## What landed

- **`MotionBlurParams{enabled, intensity, max_length}`**. `intensity` 0 is the
  off switch (`enabled` folds into it at push time).
- **`FrameUniforms::prev_view_proj` at offset 80**, in the MIDDLE of the block,
  so the tonemap pass can declare a std140 PREFIX (144 B) instead of redeclaring
  forty floats. Every member after it moved by one mat4 on BOTH sides.
- An 8-tap box average along the capped velocity, centred on the pixel (the
  shutter is open either side of it).
- `motion_prev_uv()` / `motion_smear()` are the CPU mirrors — the reprojection
  and the cap are the parts with the content.
- Scene data (`motion=`, `motion_intensity=`, `motion_length=`), component
  fields, `extract_post_process`, an Inspector block, 2 Arabic keys.

## Traps this turn
1. **The `static_assert(offsetof(...))` block in Renderer3D.hpp did its job.**
   Inserting `prev_view_proj` failed ten of them at once with the field names in
   the message — exactly what they exist for ("a field inserted in the middle
   shifts everything after it, and a sum only notices when the shift changes the
   total"). Updated all of them, plus `brdf.glsl`, together.
2. **A GPU test needs GEOMETRY.** The first plan was to reuse `render_empty_scene`
   — but with no geometry every depth is the far plane, the reprojection reports
   zero velocity BY CONSTRUCTION, and the test would have passed with the whole
   stage deleted. Added `render_cube_scene` (a cube at the origin) so the depth
   buffer has a real surface.
3. **My sign assumption was backwards** in the CPU test: I wrote "pulling the
   camera back moves the point toward the centre" while the setup had the camera
   coming CLOSER. The code was right; the comment and the assertion were wrong.
   Fixed both and the direction is now pinned explicitly.

## Tests — 4 new
`..._smear_is_zero_for_a_still_camera` (same matrices, and disabled),
`..._smear_follows_the_reprojection` (magnitude AND sign),
`..._smear_is_capped` (a teleporting camera), and a GPU case
`post_stack_motion_blur_changes_the_rendered_image` that renders a CUBE:
a still camera is pixel-identical, and a camera that moved is not — with the
history deliberately returned to the same state before each compared render, or
the second one would correctly see a still camera and do nothing.

**Rule 0:** never advancing the camera history (always writing the current
view-projection as "previous") fails the GPU test (252/1).

## §206 is now COMPLETE
Exposure, colour grading, bloom, depth of field, motion blur, lens effects,
tonemapping, sharpening, saturation and vignette are all implemented, all
switchable, and all reachable from a scene — the §263 success criterion.

## The last deferred post-FX item
Phase 27's deferred list had one entry left besides a grading LUT: "exposure /
tonemap-mode as scene data". It was deferred because "exposure is a display
preference, not scene data — never persisted per scene, because the editor's
golden pixel count is pinned to its default".

The resolution is a SENTINEL, not a change of heart: `exposure = 0` and
`tonemap = -1` mean "the scene says nothing", so `extract_post_process` applies
them only when a scene actually names them. The default scene is untouched, the
golden pixels hold, and a level CAN still author its own exposure. The writer
emits the keys only when authored, so no existing scene gains a claim it never
made.

- `Runtime::set_tonemap_mode` — a narrow wrapper like `set_exposure`, because
  `renderer()` is const by design. The operator is a CLOSED SET, so an unknown
  value is refused rather than defaulted.
- The two live on the renderer rather than in `PostFxParams`, so they are
  applied after `set_postfx`.
- Editor: an exposure slider whose 0 shows "(renderer default)", and a combo
  whose first entry is "Not set". Factory bounds match the loader's.
- The push test now also asserts the OPT-IN contract: a scene with no
  `PostProcess:` line must not reset the renderer's exposure or operator, or
  loading any level would undo a display preference the author set.

## CliffStory registered (flagged six times, now done)
`Samples/CliffStory` was a complete 2D story-climb with its own README, built and

## The trap this turn
Two localization tests failed on the new keys: `tonemap_aces` and
`tonemap_reinhard` are proper nouns, so their Arabic value is legitimately
identical to the English one — and `localization_every_key_has_both_languages`
reads an identical value as "Arabic falls back to English", while
`localization_arabic_values_carry_real_arabic` reads it as "no Arabic at all".

The fix is the mechanism the test already has for exactly this: a new entry in
`same_in_both_languages()`. That list is for values identical in BOTH languages;
`latin_allowed_in_arabic()` is the other one, for Arabic values that merely
CONTAIN a Latin token. Adding to the wrong list would have silenced the check
without recording why. `tonemap_exponential` ("أسي") and `tonemap_linear` ("خطي")
are translated normally — only the two eponymous operators are exempt.

engine already uploads.

- Scene keys `lut=` and `lut_strength=` (the strength is written only alongside a
  path — on its own it is a claim that changes nothing). Editor: a path field, a

## The trap worth keeping
**The strength is folded to 0 at push time when no LUT is bound.** The slot then
holds the renderer's 1x1 white texture, so an authored `lut_strength` with no LUT
would grade the entire frame toward WHITE. Same shape as `bloom_on` folding the
intensity. A test that only exercised the "no LUT bound" path would have passed
with the whole stage deleted, so the GPU test **uploads a real LUT** (constant
red) and asserts the frame goes red-dominant.
