# 2026-10-02 — Phase 27: the post-processing stack (§206)

## What was done

Design §206 specifies the post stack (Exposure · Color Grading · Bloom · DOF ·
Motion Blur · Lens Effects · Tonemapping · Sharpening) and requires every stage
to be individually switchable; §263 lists "post process" as a renderer success
criterion. The engine had Exposure, four tonemap operators and a two-field
"post FX" tail (saturation, vignette) — and **none of it was reachable from a
scene**. This phase closes that.

### Renderer (`Engine/Rendering`)
- `PostFxParams` grows from two floats to three nested stages: `BloomParams`,
  `ColorGradeParams`, `SharpenParams`. `saturation`/`vignette` stay first so
  `PostFxParams{1.15f, 0.28f}` in `Samples/MedievalVillage` keeps its meaning.
- **A real 4-level bloom chain** (`kBloomLevels = 4`), not a single-shader glow:
  `HDR →prefilter(soft knee)→ L0(½) →13-tap downsample→ L1(¼) → L2(⅛) → L3(1/16)`,
  then the tonemap pass sums all four with bilinear taps and `intensity`.
  The chain **stops at the smallest level** — a bilinear fetch of a half-size
  level IS the 2×2 tent filter an explicit upsample pass would apply, so there
  is no upsample pass and no additive blending (this RHI puts blend state on the
  render-pass attachment, not the pipeline).
- One shader pair serves both stages: `Samples/Basic3D/shaders/bloom.{vert,frag}`,
  with the kernel chosen by a push-constant mode flag. One pipeline, one
  descriptor layout, one render pass, four textures/framebuffers.
- `enabled=false` costs nothing: no bloom pass is recorded, and the tonemap
  shader's `bloom_intensity > 0` guard means the bloom bindings are never read.
  The HDR view is bound in their place so every binding is still a valid image.
- Colour grade runs in **HDR before the tonemap operator** (where §206 puts it:
  a contrast curve applied after the tonemap clips the highlights the operator
  just rolled off). Sharpen is an unsharp mask on linear HDR, applied **before**
  the bloom add, inside the existing pass — four extra texture fetches, no passes.
- Implemented order: `sharpen → bloom add → exposure → grade → tonemap → gamma →
  saturation → vignette`. §206 lists exposure before grading and bloom after it;
  the bloom add sits before exposure because the prefilter reads the raw HDR
  target, so its threshold is in pre-exposure units.
- Tonemap push block grew 16 → 64 bytes (16 floats) and the tonemap descriptor
  layout grew 1 → 5 bindings (HDR + 4 bloom levels).
- CPU mirrors for every new shader function: `bloom_prefilter`,
  `bloom_downsample`, `unsharp_hdr`, `apply_color_grade`, and
  **`apply_post_chain`** — the last mirrors the whole fragment body, so the stage
  ORDER is testable, not just the individual stages.

### Scene / runtime / editor
- `PostProcessComponent` (`RuntimeSceneTypes.hpp`, flat floats — this header is
  included by the editor and the tools, and pulling `Renderer3D.hpp` and the RHI
  into all of them to carry 15 numbers is the wrong trade; `SkyComponent` set the
  precedent).
- `PostProcess:` line in `.nfscene`: parse (per-key range validation via a
  renamed `optional_float_in_range`), write, prefab/play clone. Written **only**
  when the component exists, so a scene that never heard of it round-trips
  byte-identical.
- `Runtime::extract_post_process()` pushes the block into the renderer, called
  from both render paths beside `extract_sky()`. A scene with no component
  leaves the renderer's state alone (does not reset it).
- Editor: `SetPostProcessCommand` (undo/redo), `make_post_process_command`
  (validated factory, same bounds as the loader), `EditorApp::set_post_process`,
  an Inspector panel, and an Add-component menu entry. Undo of the edit that
  created the block **removes** the component.
- 23 new Arabic localization keys.

## Rule 0 — three breakages, watched to fail

1. `bloom_on = false` → the two GPU bloom tests FAILED (30/0 → 28/2).
2. `extract_post_process()` removed from `render_offscreen` → the runtime push
   test FAILED (5/0 → 4/1).
3. Grade moved after the operator in `apply_post_chain` → **the ordering test
   did NOT fail.** It compared the chain against "grade the finished LDR image",
   and the break produces "grade right after the operator, before gamma" — a
   different wrong answer it was blind to. Rewritten to compute *both* wrong
   orders; the re-run then fails as intended (29/1).

## Lessons worth keeping

- **`##suffix` must be UNIQUE, not merely present.** The first draft of the
  Inspector panel gave all fourteen widgets `"##pp"`. An ImGui ID is the text
  after `##`, so every slider shared one ID. `Scripts/audit_imgui_ids.py` does
  not catch it (it flags *bare* labels), and ImGui's own duplicate detector is
  hover-based, so no automated run would have seen it. A `##suffix` makes an ID
  unique only if the suffix is.
- **A test that names an ordering is not a test that pins it.** Enumerate the
  orderings you are ruling out, not just the one you had in mind.
- **Bloom levels must be declared as reads on the tonemap pass.** Without that
  the graph leaves each level in the layout the bloom pass wrote it in and the
  tonemap pass samples a colour attachment — a validation error on one driver, a
  garbage glow on another.
- **Never build a `.nfscene` demo without `Name:` lines.** `Runtime.cpp:385-410`
  synthesizes a name from the entity's KIND, so two mesh entities are both
  `"Mesh"` — which is invisible until it breaks the editor's save/load structure
  check (see the findings below). Give every entity a name.
- **A windowed editor run in this sandbox can occasionally stall** and be killed
  by `timeout` (observed once, rc=124, then rc=0 on an identical re-run with no
  change). If a windowed run times out, re-run before suspecting the change.
- `cmd /c`-free redirection (`> log 2>&1` in bash) is fine for capturing editor
  logs; the PowerShell `*>` trap in MEMORY.md is about PowerShell specifically.
- A per-iteration variable captured by `[&]` in a loop of render-graph lambdas is
  captured by REFERENCE and every pass then reads the LAST iteration's value.
  Capture `push`/`level`/the level's size by value.

## Deliberately deferred (named, not silently skipped)

Depth of field, motion blur, lens effects (each wants data the renderer does not
keep — a physical lens model + the depth target as a texture; a velocity buffer
the deferred path does not write). A per-stage colour-grading LUT (wants an
asset type + loader + UI). `exposure` and the tonemap mode as scene data (they
are renderer setters with golden pixels pinned to their defaults).

## Two engine findings surfaced by the demo (filed in `COORDINATION.md`)

Building `C:/Users/abdal/OneDrive/Desktop/PostFxDemo` (a real `nf new` project, not a
sample) to prove the stack end-to-end turned up two pre-existing defects that have nothing
to do with the post stack:

1. **`.nfmat` `emission:` rgb is inert.** `lighting.frag:100` is
   `vec3 emissive = albedo * emission_strength;` — the colour is parsed
   (`MaterialAsset.cpp:82`), written (`:127`) and round-tripped, and never read.
   `gbuffer.frag:25` documents `misc` as `emission.rgb, useBaseColorTex` and only `misc.w`
   is ever sampled. A material with `base_color: 0.06 0.06 0.07` + `emission: 1 0.82 0.45`
   + `emission_strength: 7` renders a NEAR-BLACK cube. The demo works around it by putting
   the glow colour in `base_color`. Fixing it properly changes every scene with
   `emission_strength > 0`, so it needs a golden-pixel pass — not a drive-by edit.
2. **`scenes_equal_structure` compares the wrong pair.** `Runtime.cpp:385-410` synthesizes
   a name from the entity's KIND for every entity lacking a `Name:` line, so two meshes are
   both `"Mesh"`. `PlayMode.cpp:156` indexes by name on the stated assumption that names are
   unique; the last one wins and the check reports `transform values differ for 'Mesh'` on a
   scene that round-tripped fine, making the editor exit 1. Adding unique `Name:` lines is
   the workaround. `Panels.cpp:688` already works around the same collision for its glyph,
   so the non-uniqueness was known and handled only in the display layer.
