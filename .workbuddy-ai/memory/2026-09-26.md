# 2026-09-26 — Editor UI/UX overhaul

## What was done
Full visual + usability pass on the ImGui editor shell, then verified in every
run mode.

### New files
- `Editor/include/NF/Editor/UiTheme.hpp` — the semantic colour layer
  (`theme::danger/success/warning`, text ladder, surfaces, axis colours,
  `theme::rgb()`). `theme::accent()` is DECLARED here and DEFINED in
  `Toolbar.cpp` (next to the settings object it reads), so the header stays free
  of `ToolbarUi.hpp`.
- `shots/editor_ui_overhaul_{en,ar}.png` — captures of the result.

### Changed
- `UiBackend.cpp` — `apply_forge_theme()` replaced the old inline style block.
  Five-step surface ladder (void #14161B → panel #1B1E24 → raised #22262D →
  control #2A2F37 → hover #343B45 → active #3E4652), accent family
  (selection/headers/buttons/sliders/tab overline), semantic fixed colours so a
  destructive action never inherits the user's accent. New in 1.93 and used

  `CheckboxSelectedBg`, `InputTextCursor`, `UnsavedMarker`,
  `DragDropTargetBg`, `DockingSeparatorSize`, `TabBarOverlineSize`,
  `WindowMenuButtonPosition = None`.
- **Font unified to 16px** (`kUiFontSize`): Latin was 15px and the merged Arabic

- `Panels.cpp` — bottom **status bar** (`BeginViewportSideBar` Down): mode dot +
  Editing/Playing, scene name + dirty star / "Saved", entity + selection counts,
  FPS + frame ms, validation badge. Plus a **viewport orientation gizmo**

- `Toolbar.cpp` — brand mark, `toolbar_group_gap()`, `icon_button` gained a

- `main.cpp` — wired shortcuts the menus had always *printed* but nothing
  listened for: Ctrl+N / Ctrl+I / Ctrl+E, plus F1, Ctrl+P (play/stop toggle),
  X (gizmo space), Ctrl+Shift+Z (redo). Added `--screenshot <file.bmp>`.
- `Localization.cpp` — 10 new keys; **removed 3 duplicate rows**.

## The important discovery: headless does NOT run the UI
`ui_frame()` is called inside `if (!cfg.headless)` in `main.cpp`, so
`--headless --validation` never records an ImGui frame and **cannot** catch a UI
regression. Real UI verification needs a bounded **windowed** run —
`NOVAForgeEditor.exe --scene … --frames 125 --validation` — which self-terminates
and is safe to launch from a tool call. Also note `automation = (max_frames != 0)`,
so every bounded run runs the automation script.

## Pre-existing issues (NOT caused by the UI work — proven by A/B)
Ran the same windowed command with the new UI drawing compiled out
(`NF_NO_NEW_UI=1` guard around the status bar + gizmo): **identical** results.
- 24 Vulkan validation errors in windowed runs (`vkDestroyImageView/Image/
  Framebuffer: can't be called on … in use by VkCommandBuffer`, plus
  `vkResetDescriptorPool` in use). 7 already at 3 frames. Headless = 0. The
  frames-in-flight change (`e79d6f2`) is the obvious suspect: this is the same
  family as the 2026-09-22 `cmd_view` fix. `NFSampleBasic3D --frames 60
  --validation` is clean, so it is editor-specific, not core-present.
- `Viewport drag undoes cleanly` fails **windowed only**, deterministically
  (3/3 runs), passes headless. The automation is frame-indexed (`f == 11`), so
  this is the windowed/headless scheduling difference the PROJECT.md note
  already warns about, in the other direction.
- `Content/Materials/Default.nfmat` is committed as `base_color: 1 0 0 1` (pure
  red) — from the initial commit. The default scene's ground and cube render
  red, which looks like a rendering fault to anyone opening the editor.

## New tool
`--screenshot <file.bmp>` writes the last composited frame (scene + FULL UI,
1280x720, 24-bit BMP) and exits. It reuses the automation's UI-over-scene
composite — the only place in a frame that holds scene AND UI in one image.
24-bit on purpose: the alpha of a 32-bit BMP is treated as transparency by some
viewers, which shows the whole capture blank. BMP rather than PNG because the
engine links stb_image (a reader) and no image writer. Convert with a small
Python BMP→PNG script (zlib) — see `.workbuddy-ai/tmp/bmp2png.py`.
`--screenshot` without `--frames` defaults to 90 frames so there is a "last frame".

## Round 2 (afternoon) — FileSystem panel: overlap fix + move to the left column

Lead report (Arabic): "look how the UI runs into itself — put it on the left, here
— I marked where in red — fix everything". Two screenshots of the bottom dock.

### Root cause of "داخل في بعضه" (the UI running into itself)
`FileSystemPanel.cpp` was laid out for ONE dock size and nothing else:
- a **fixed 230px favourites column** (`BeginChild("##fsleft", ImVec2(230, …))`),
  so in any narrow dock the file list got a few pixels and the two panes read as
  painted on top of each other;
- **`PushItemWidth(-220.0f)`** on the filter — a negative width, so it collapsed
  to nothing when the panel was narrower than 220px;
- the **breadcrumb + six buttons on one line**, which simply ran off the panel
  edge (ImGui clips, so a clipped button looks like a missing one);
- the panel's own **"FileSystem" tab button duplicating the dock tab label**
  directly above it — two identical strings, one above the other, which is what
  actually reads as "the UI is overlapping".

### Fixes
- Panel is now **width- and height-aware**: `panel_w`/`panel_h` are measured
  once, then `compact` (stack the split, ellipsise the crumb), `show_root_combo`,
  `show_import`, `show_status` drop optional rows as the dock shrinks. The file
  list is the one thing that never shrinks to nothing.
- Split is **stacked when narrow**, side-by-side with a *proportional* column
  (`clamp(avail*0.34, 150, 250)`) when wide.
- Internal switcher renamed **"FileSystem" → "Files"** (`files` key) — a view
  switcher must not repeat the dock title.
- Nav row is placed against a **real x-budget** with `small_btn_w()`
  (text + FramePadding.x*2 — SmallButton adds no inner padding). Controls that do
  not fit **wrap to the next row**, never clip. Priority on the nav row:
  arrows → path → refresh → view toggle.
- **`GetContentRegionAvail()` must be read AFTER `SameLine()`.** Before it, ImGui
  has already advanced the cursor to the next line, so it reports the FULL width
  rather than what is left on the row. Measuring first placed the view toggle past
  the right edge where the clip rect swallowed it — drawn, invisible, and it cost
  a debugging round.
- Status line was feeding **`ui::tr()` straight to `TextDisabled`** → unshaped
  Arabic (letters reversed and unjoined, digits misplaced). Now composed logical
  then `ui::shape_arabic()` once. Same defect class as the old "فأظشرألا عوطق"
  toolbar label. A grep for `ui::tr(` in `Editor/src/` shows every remaining site
  feeds `AVF()`/`shape_arabic()`, so this was the only live one.
- Import job lines and the empty-folder hint are `TextWrapped`; the selected-path
  suffix is ellipsised to the room left on the line.

### Dock layout (Panels.cpp)
Left column is now **outliner on top, FileSystem underneath** (0.24 wide, split
0.50/0.50); Console keeps the bottom-centre strip. This is what the lead asked
for and it fills the dead space a short outliner leaves. `"Assets"` is still the
FileSystem window's dock ID.

### Verified
- Build 42/42; UITests 39/0; EditorTests 217/0; full sweep green.
- Headless 125f: 1 pre-existing failure, 0 validation errors, 0 leaks.
- Windowed 125f: 2 pre-existing failures, 24 pre-existing validation errors,
  0 leaks, UI overlay proof OK (777253 px differ). All unchanged from the
  pre-change baseline — the layout work caused no regression.

### Note for the lead
The dock layout is rebuilt every launch (`io.IniFilename = nullptr`, a deliberate
choice in `Editor/DESIGN.md`), so **a panel arrangement the user drags is lost on
restart**. Worth revisiting if the default ever has to satisfy more than one
window size.

## Round 3 — "Programmer error: 2 visible items with conflicting ID!"

Lead sent a screenshot of the ImGui red popup over the Console panel, with the
category chips "Core"/"Core" and "RHI"/"RHI" highlighted red. Yes — a real bug.

### Cause
`Panels.cpp` console rows drew the category tag as
`ImGui::SmallButton(category_name(m.category))` inside the per-line loop. A
SmallButton's ID is its label, and every row in the same category has the SAME
label — so N visible "Editor" lines submitted N items with one ID. ImGui 1.93
ships `io.ConfigDebugHighlightIdConflicts = true` (imgui.cpp:1762), hence the
popup.

It only appeared now because the conflict needs **two items of one category
visible at once**, and because ImGui's detector is **hover-based**: see
`ItemHoverable()` — "this is specifically done here by comparing on hover
because it allows us a detection of duplicates that is algorithmically extra
cheap". So it fires only while the pointer is over the item, which is why the
automation run never caught it and the lead did.

### Fix
A chip is a LABEL, not a control. `draw_category_chip()` (Panels.cpp) draws a
rounded rect + text with the draw list and reserves the space with a Dummy — it
consumes no ID at all, so the class of bug cannot come back. Also hardened the
reflected-inspector field loop with `PushID(index)` (property labels could
collide the same way).

### Safety net
`main.cpp` now logs once per session when
`ImGuiContext::DebugDrawIdConflictsId != 0` — the same condition that shows the
popup, but visible in a log instead of only in a screenshot. Requires
`<imgui_internal.h>` in main.cpp.

Audited the rest: FileSystemPanel row widgets all sit inside `PushID` scopes
(9 of them); AssetBrowser.cpp has no ImGui calls (pure logic); Toolbar/inspector
labels are unique or carry `##suffix` ids; the new shortcuts window's tables are
keyed by unique group keys. Console chip was the only live conflict.

### Verified
Build 42/42; headless 125f unchanged (1 pre-existing failure, 0 validation
errors, 0 leaks); windowed 125f unchanged (2 pre-existing failures, 24
pre-existing validation errors, 0 leaks, UI overlay proof OK); no ID conflict
logged.

## Round 4 — second ID conflict (History list), an audit tool, and layout persistence

### The conflict (lead's 2nd screenshot)
FileSystemPanel's History tab built each row with `PushID(folder.c_str())` — the
folder PATH. `back_stack` + current + `forward_stack` legitimately contains the
same path twice (A -> B -> A), so two rows submitted one ID. Fixed by keying on
the row's POSITION (`hist_index++`); same change applied to the favourites list.

### A detector, because ImGui's is hover-only
`ItemHoverable()` only flags a conflict while the pointer is over the item, so
no automated run can ever see one — the lead found both of these by hand.
`ThirdParty/CMakeLists.txt` now has an opt-in `NF_IMGUI_ID_AUDIT=ON` that defines
`IMGUI_DEBUG_HIGHLIGHT_ALL_ID_CONFLICTS` on the imgui target (ImGui's own comment:
"THIS WILL SLOW DOWN DEAR IMGUI. DON'T KEEP ACTIVATED."). With it on, main.cpp
walks `DebugDrawIdConflictsHighlightSet` every frame and logs each duplicate ID
once per run.

**Validated the tool itself** (this is the part worth remembering):
- buggy `PushID(folder)` + a forced duplicate path -> logs `duplicate ID 0xDF3C25A9`
- fixed `PushID(hist_index)` + the SAME forced duplicate -> logs nothing
So the detector is proven to catch the class, not just silent.

To reconfigure: `cmake build/DebugNinja -DNF_IMGUI_ID_AUDIT=ON|OFF` (needs the
nfb.sh env block — reg.exe is blacklisted, see the top of this file).

### Layout persistence (the "engines remember your layout" gap)
`ui_init(hwnd, persist_layout)` now sets `io.IniFilename` to
`%APPDATA%\NOVAForge\editor_layout.ini` for a HUMAN session (`--frames 0`) and
leaves it null for a scripted run, so automation screenshots stay deterministic.
`Panels.cpp` only builds the default layout when `DockBuilderGetNode()` shows no
restored split tree, so a saved arrangement is not thrown away. View > Reset
layout forces the default back.

**Gotcha: `DockBuilderFinish()` does NOT mark the ini settings dirty.** Without an
explicit `ImGui::MarkIniSettingsDirty()` the default layout was never written —
the file only appeared if the user happened to drag a splitter.

Verified by writing sentinel `SizeRef` values into the ini and relaunching: they
survived, i.e. the layout was loaded, not rebuilt. (The interactive path itself
cannot be exercised from a tool call — the sandbox has no interactive desktop and
a maximised window blocks before RHI init — so the test used a temporary
`persist_layout = true` override with `--frames`, then reverted.)

### Outliner entity-type tint
`OutlinerKind` (Camera > Light > Sky > Mesh > Empty, most specific first) added to
`OutlinerRow` and populated in `build_outliner_rows`. Panels tints the row label
— a COLOUR, not an icon glyph: the UI font has no icon glyphs (Toolbar.cpp
learned that: every typed symbol rasterised as a box) and drawing a glyph over the
label would fight the tree node's hit box, which selection / drag & drop / the
context menu all hang off. Only the special kinds are tinted; a mesh keeps the
theme colour so the tree does not become a colour chart.

### Verified
Build 42/42; full sweep **1647 passed / 0 failed / 2 skipped** across 26 suites;
headless 125f unchanged; windowed 125f unchanged (UI overlay proof OK); no ID
conflict logged.

## Round 5 — "resizing the window freezes the engine" (VK_ERROR_DEVICE_LOST)

Lead's log: an endless stream of `vkWaitForFences failed: VK_ERROR_DEVICE_LOST` +
`vkQueueSubmit … VK_ERROR_DEVICE_LOST`, then a freeze.

### Reproduced, and the root cause was NOT the device-loss
Added `--resize-test` (window `nf::Window::resize()` through a size cycle every 25
frames) — the only way to exercise the resize path without a human dragging the
window edge (a P/Invoke resize helper from outside was sandbox-blocked). First run
reproduced a SEGFAULT, and the log named the real bug:

```
vkCreateSwapchainKHR(...) returned VK_ERROR_NATIVE_WINDOW_IN_USE_KHR
Failed to create swapchain
vkAcquireNextImageKHR(): Invalid VkSwapchainKHR Object   ->  segfault
```

`Swapchain_Vk.cpp` passes `create_info.oldSwapchain = VK_NULL_HANDLE`, so the OLD
swapchain has to be gone before the new one is asked for. main.cpp did the
opposite: it created the new swapchain while the old still existed, the driver
refused, `fresh` came back null, the whole `if (fresh)` body was SKIPPED, and the
editor kept rendering into the stale handle. On another driver the same sequence
surfaces as the lead's DEVICE_LOST stream.

### Three fixes
1. **Resize teardown order** (main.cpp): `ui_fbs.clear()` -> `render_finished.clear()`
   -> `swapchain.reset()` -> THEN create. Framebuffers before the swapchain: they
   hold views OF its images. And `if (!fresh)` now logs and exits with a reason
   instead of silently continuing.
2. **`nf::rhi::device_lost()`** (new, latched): `vk_check_impl` and
   `VulkanFence::wait` set it on VK_ERROR_DEVICE_LOST. The editor checks it each
   frame and stops with a message — a lost device is terminal, so the old
   behaviour was an infinite error loop, which is what "frozen" actually was.
3. **The real validation-error source** — the two remaining error families were a
   broken lifetime contract, not resize-specific:
   - `Viewport.hpp` states plainly "the caller must wait_idle() first … so no
     in-flight command buffer ever references the destroyed texture". The
     every-frame `wait_idle()` was removed for performance and the fence wait was
     left AFTER `ensure_viewport_target()` — so on a resize frame the old target
     was destroyed under a pending `cmd_view` AND the main pass that presents from
     its view. Now both fences are waited BEFORE the call, and only on frames that
     actually recreate the target (per-frame cost unchanged).
   - The UI-overlay proof block resets the UI descriptor pool via
     `UiRenderer::render()` while the frame's own `cmd_main` is still in flight.
     It now waits `frame_fence` first.

### Result
| run | before | after |
|---|---|---|
| windowed 125f `--validation` | 24 validation errors | **0** |
| windowed 400f + 15 resizes | 32 errors, DEVICE_LOST/segfault | **0**, clean exit, 0 leaks |

This also retires the "pre-existing 24 validation errors" note that had been in
this file since the first UI round — they were never a UI problem, they were this
lifetime hole. `--resize-test` stays as the regression driver for it.

`frame_fence` is waited but never reset in these new gates: the main pass resets
it immediately before its own submit, and resetting it early would make that
later wait block forever on a fence nobody signals.

## Round 6 — third ID conflict (Import section) + a STATIC audit so this stops being whack-a-mole

### The conflict
`FileSystemPanel.cpp`: `CollapsingHeader(AV("import"))` and, inside it,
`Button(AV("import"))` — the same label, therefore the same ID, in the same
window. Expanding the section made two visible items share an ID. Fixed with
`##fsimport_tools` / `##fsimport_run`.

### A static audit found two more that no screenshot had reached yet
`Scripts/audit_imgui_ids.py` (new, committed) flags any `AV("key")` used as a BARE
label by more than one non-menu widget in a file. `##suffix` makes an ID unique
and `MenuItem` only ever lives in its own popup, so neither is flagged.

It found, beyond the reported one:
- **Six bare `Checkbox(AV("enabled"))` in the inspector** (sky, destructible,
  particles, cloth, character, script) — every one inside a DEFAULT-OPEN
  collapsing section, so any entity carrying two of those components collided.
  This was a real, reachable bug nobody had hit yet. Each now carries its own
  `##…_enabled`.
- **`Combo(AV("material"))` vs `CollapsingHeader(AV("material") + "###Material")`** —
  the header's id is literally `Material`, which equals the combo's ENGLISH label,
  so it collided **in English only** (the Arabic label differs). The nastiest kind:
  it would never reproduce in an Arabic-UI session. The combo is now
  `##material_asset`.

Then suffixed the five cross-window candidates (`autosave`, `browse`, `cancel`,
`close`, `sky_preset` — all in different dialogs/menus, so not broken today) so the
script reports zero. A report that always prints the same false positives gets
ignored; a clean one makes the next hit meaningful.

### Verified
- `python Scripts/audit_imgui_ids.py` -> "No same-window bare-label collisions found."
- Runtime audit (`-DNF_IMGUI_ID_AUDIT=ON`) with the Import section forced open AND
  `show_import` forced true (the first attempt proved nothing — the section was not
  rendering at that panel height, so the audit had nothing to look at): **0
  duplicates**. That is the lesson: a clean audit only means something once you
  have confirmed the code path actually executed.
- Build 42/42; sweep 1647/0/2; headless unchanged; windowed 0 validation errors;
  windowed + 15 resizes 0 validation errors, 0 leaks.
