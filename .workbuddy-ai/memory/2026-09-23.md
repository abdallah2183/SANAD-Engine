## Mesh import: the engine can now read every format it writes

**Reported:** "why can't the engine import assets from all formats yet, the model can't
do it — fix it, make it usable and developable."

**Diagnosis (all confirmed in source, not assumed):**
- `MeshExport` wrote **six** formats (`.nfmesh/.obj/.stl/.ply/.gltf/.glb`);
  `GltfImport` read **one** (`.gltf/.glb`). Exporting to OBJ produced a file the
  engine could not open again.
- **The editor's Import dialog was worse than useless for models:** its file
  filter offered `Models (*.gltf;*.glb;*.nfmesh)` while
  `ImportQueue::type_for_extension` returned `Unknown` for `.gltf`/`.glb` — so
  picking a glTF in the dialog produced *"Unsupported extension"*. Two
  hand-maintained lists had drifted apart. It also advertised
  `*.wav;*.ogg;*.mp3`, which the queue never accepted either.
- `NFModelImporter` could read glTF, but it is a separate CLI not wired to the
  editor.

**Built:**
- **`Engine/Assets/{include/NF/Assets/MeshImport.hpp, src/MeshImport.cpp}`** — one
  read path. OBJ (groups, `usemtl` slots, negative indices, n-gon fan,
  index-triple dedupe), STL (binary + ASCII), PLY (ASCII + binary LE/BE, list
  properties, unknown-element skipping), `.nfmesh` pass-through, glTF/GLB
  delegate. Extension wins, content sniffing is the fallback, contradiction
  fails loudly. Ledger: `faces_skipped`, `vertices_skipped`,
  `primitives_skipped`, `anim_channels_skipped`, plus `warnings` naming what the
  format itself cannot carry.
- `MeshImportResult` now owns the payload; `GltfImportResult` is an alias → every
  existing caller/test untouched.
- **Editor:** `ImportQueue` accepts every model extension and cooks to `.nfmesh`
  (one file per mesh, `<stem>.nfmesh` + `<stem>_1.nfmesh`...), writes
  `written_paths` + `warnings` on the job, and the dialog filter is derived from
  the reader's format table. `EditorApp::watch_imported` watches every written
  path.
- **CLI:** `NFModelImporter` → `import_mesh_file`; all pinned report lines/exit
  codes preserved, plus a `format:` line.
- **Docs:** new `Docs/Asset_Import.md` (EN + Arabic summary), ROADMAP bullet
  under Phase 14.

**Two latent bugs found and fixed while deduplicating:**
1. `import_gltf_memory/file` set `result.format` and then `result =
   convert_parsed(...)` — the assignment discarded it, so `format` was always
   `Unknown`. Caught by `mesh_import_glb_round_trip`.
2. The local smooth-normal helper added `base_vertex` to indices that already
   carried it, so every glTF primitive after the first computed normals from the
   wrong triangles. Caught while moving the helper to MeshImport.cpp.

**Verification:** full `nfb.sh` build clean; full sweep **1596/0/2 across 26
suites** (reconciles: summary.txt 1571 +16 AssetTests +5 EditorTests +4
ToolTests). Editor headless `--headless --frames 125 --validation` → exit 0,
`Validation errors: 0`, `Alive RHI objects: 0`. New tests: 16 AssetTests
round-trips, 5 editor model-import cases, 2 CLI cases.

**RHITests — not my regression, but I fixed it.** `shader_async_compile_via_job_system`
failed 4/4 deterministically. `RHITests` links `NFCore NFRHI NFRendering NFScene
NFEcs NFRuntime` — **not `NFAssets`** — and `Engine/Rendering`, `Engine/Jobs`,
`Tests/RHITests` are unmodified vs HEAD, so my diff cannot reach it. Root cause:
the test slept a fixed 300 ms for an async compile that shells out to `glslc`,
measured at **535–556 ms** on this box. Now a bounded poll of `update()`; the
assertion is unchanged. 206/1 → 207/0. Filed under `## Requests` in
COORDINATION.md as outside-column.

**Not done / open:**
- **FBX: deliberately not vendored** (documented G2 decision, glTF-first route
  with the shipped Blender add-on). This is a lead-level decision if Abdal wants
  direct FBX.
- **Audio is still not importable** — needs an `AssetType` + registry/browser
  support; the filter no longer pretends otherwise.
- **`Docs/` sync:** `README.md`/`README.ar.md`, `website/index.html`,
  `index.html` and the design doc were **not** updated with the import pipeline;
  only `ROADMAP.md` + the new `Docs/Asset_Import.md` were.
- No commit (project rule: no commit without explicit lead order).

## Session 3b — materials and textures on import (same day, continued)

**Asked:** "كمل تطوير وتحسين" (continue developing and improving).

**Chose the next gap by what actually blocks a developer:** the importer brought
geometry and nothing else, so an imported model arrived grey. Materials and
textures were being *dropped*, which is the same class of silent loss the first
half of this session was about.

**Recon that made it cheap:** `MaterialAsset` (`.nfmat`) already carries an
`albedo` logical path, and `Runtime` already loads it and flips
`use_base_color_texture` itself. So the whole feature needed **no engine
change** — only the importer filling the payload and the editor writing the
files.

**Landed:**
- `MeshImportImage` (name / source / extension / original encoded bytes) +
  `MeshImportResult::images` + `images_skipped`. `image_extension_for_bytes()`
  sniffs the container from magic numbers; TGA returns empty on purpose (it has
  no signature) and callers fall back to the source's own extension.
- `GltfMaterialInfo` gained `emissive`, `emissive_strength`, `albedo_image` and a
  per-material `dropped` ledger.
- **glTF:** images extracted from a GLB BIN chunk, a base64 `bufferView`, a
  `data:` URI, or an external file beside the `.gltf` (percent-decoded). The
  base-colour map resolves to an image index; normal / metallicRoughness /
  occlusion / emissive maps, specular-glossiness, clearcoat, sheen, transmission,
  iridescence and non-opaque alpha are all NAMED as dropped.
- **OBJ:** a real `.mtl` reader (`Kd`, `Ke`, `d`/`Tr`, `map_Kd` with options;
  `Ka`/`Ks`/`Ns`/`Ni`/`Tf`/`illum` and every non-base-colour `map_*` recorded as
  dropped). `mtllib` is pre-scanned in its own pass so a file that puts `usemtl`
  before `mtllib` still gets its parameters. `material_slot` is now the index of
  a real material in first-use order.
- **Editor:** a model import also writes each image as a registered texture under
  `content://Textures` (+ cache copy) and one `.nfmat` per material under
  `content://Materials` with `albedo:` pointing at the texture. Write order is
  mesh → textures → materials so `written[0]` stays the primary destination.
  `ImportJob::written_paths` became `written` (path + type) and
  `EditorApp::watch_imported` dispatches per type.
- **CLI:** `--info` prints materials with their dropped ledger and the image
  list; the geometry-only cook now says out loud how many materials and images it
  is NOT writing.
- **Docs synced:** `Docs/Asset_Import.md`, `ROADMAP.md`, `README.md` (the
  "glTF + FBX" claim was false — FBX is not supported — and is now the six real
  formats), `README.ar.md` (new docs link), `website/index.html` and
  `index.html` (feature card + phase list, AR and EN).

**Bug found by a failing test, and the reader was right:** my OBJ fixture used
`f 1//1 2//2 3//3` with a single `vn`, so references 2 and 3 pointed past the end
of the normal pool. The reader rejected the face — correctly. The diagnosis did
expose a real gap though: a face rejected on its *third* reference left the first
two vertices behind as orphans, counted in the asset and in every submesh's
`vertex_count`. Now rolled back, with a test
(`mesh_import_obj_v_slash_slash_vn_and_face_rollback`) that pins both facts.

**Verification:** full build clean; full sweep **1607/0/2 across 26 suites**
(1596 + 7 AssetTests + 3 EditorTests + 1 ToolTests); editor headless
`--headless --frames 125 --validation` → exit 0, `Validation errors: 0`,
`Alive RHI objects: 0`.

**Still open:** FBX (lead decision, unchanged); audio import (needs an
`AssetType`); the import creates assets but does not assign a material to an
entity — that stays an explicit editor action. No commit (project rule).

## Session 3c — a complete game built with the engine's own tools

**Asked:** build a full game *inside* the engine, using only the engine's tools, step by step, with a
runnable result and no hand-waved "here are some files".

**Deliverable:** `C:/Users/abdal/OneDrive/Desktop/SanadArena` — «ساحة سند», a 3D physics demolition
arena, 24 entities, built entirely through `nf` + the editor.

**The tool chain actually used, in order:**
1. `nf new SanadArena --template ThirdPerson` — the ENGINE wrote the `.nfproj` (5 mounts),
   `Content/` (registry, cube+sphere meshes, Default.nfmat, Main.nfscene) and `.gitignore`.
2. Read `RuntimeSceneLoader.cpp` to learn the scene grammar before touching anything. A `.nfscene`
   accepts exactly 13 component lines: Name, Transform, Camera, Light, Sky, Mesh, RigidBody,
   Collider, Animation, Audio, Destructible, Module, Prefab.
3. Authored `Content/Scenes/Main.nfscene` in that grammar — 24 entities: player sphere with
   `Module: PlayerController`, floor + 4 walls, 9 crates in three difficulty tiers
   (`damage_threshold` 4 / 8 / 14), a heavy `DropBall` that falls and teaches the mechanic, 3
   procedural-spin beacons, 2 audio tones, and an `OrbitCamera` targeting the player.
4. `nf cook` → cooked 4, failed 0. `nf verify` → total 4, ok 4, missing 0.
5. `nf build` → packaged 23 files + 14 shaders into `dist/` with `NFPlayer.exe` and a manifest.
6. `nf run --headless --frames 200 --validation` → 24 entities, 16 physics bodies, 9 destructibles,
   2 gameplay modules, **`destructible entity 9 came apart`** (the impact loop fired on its own),
   `Validation errors: 0`, `Alive RHI objects: 0`.
7. `NOVAForgeEditor.exe --project … --headless --frames 125 --validation` → `Scene opened in 37.9 ms`,
   `Outliner: 24 entities [Player, Sun, Sky, ArenaFloor, …]`, `cube lit pixels = 687333`,
   `draws=42 visible=21`, every `Automation: … OK`.

**Traps found, each verified by direct comparison rather than assumed:**
- **`Last frame: extracted=0 visible=0 draws=0` is the headless PLAYER path, not a broken scene.**
  A freshly scaffolded, unmodified `ThirdPerson` project prints the same. The editor run is the
  render proof (`draws=42 visible=21`).
- **`--frames 60` on the editor reports `automation=FAILED`** — the built-in harness needs ~125
  frames. Frame-budget artefact, not a defect.
- **No `Script:` line exists in the scene loader**, and no CLI flag feeds
  `Runtime::begin_input_replay()`. Gameplay logic can therefore only come from the two built-in
  modules (PlayerController, OrbitCamera) plus `step_impact_damage()`. Lua is unreachable from a
  scene — a real engine gap, filed for the scripting/runtime owners.
- **A GUI process launched from a tool call is killed when the call returns.** A detached `spawn`
  with stdio redirected to a file and `unref()`-ed survived only while the shell command ran; its log
  then stopped mid-frame with zero shutdown lines. The other shell tool available here returns **no
  output at all**, so a launch failure through it is silent. Never promise the user an open window —
  prove the load, then hand them a `.cmd` launcher (`OpenInEditor.cmd` and `PlayGame.cmd` now sit in
  the project).

**Saved as a skill:** `~/.workbuddy-ai/skills/novaforge-build-game/SKILL.md` — the full workflow, the
scene grammar, the capability list, and both traps above.

**Not demonstrated, and said so:** the player moving. Movement is input-driven and there is no
scripted-input route, so a headless run cannot show it; the user has to press the keys.

## Session 3d — «سند بورغ»: a town from a real asset kit, and a measured engine finding

**Asked:** build a NEW game (the existing `Samples/MedievalVillage` was explicitly rejected as
"old"), entirely with the engine's own tools, from the real
`C:\Users\abdal\Downloads\Medieval Village MegaKit[Standard]`, and **measure the engine's power**.

**Deliverable:** `C:/Users/abdal/OneDrive/Desktop/SanadBurg` — a walled medieval town, 522 entities,
54 real kit pieces, 8 destructible market crates (the objective), 4 animated banners, 2 synthesised
audio sources, 4-cascade shadows, real albedo textures.

**The kit ships OBJ + MTL + glTF + GLB + FBX.** FBX was never needed — the unified importer built
earlier today reads the glTF, so the "no FBX" decision cost nothing here.

**Pipeline, every step an engine binary:** `nf new` → `NFModelImporter` × 176 (**176 converted, 0
failed**) → `nf cook` (**179 assets registered, ids assigned**) → `Tools/build_map.py` (reads the
registry + each piece's measured bounds, emits the scene) → `nf cook/verify/build` (200 ok, 417 files
packaged) → `nf run` + the editor (522 entities, 222 bodies, 0 validation errors, 0 RHI leaks).

**Three real bugs found and fixed in my own map builder**, each caught by an engine message:
1. Emitted blocks without the `entity: <id>:0` line → `Expected entity line`. The loader needs BOTH
   the `---` separator and the entity line.
2. Emitted `RigidBody` without `Collider` → "physics world created with 2 bodies" instead of 222.
3. Put colliders on separate entities (correct — the kit's worst pivot offset is **1.138 m**) but then
   attached `Destructible:` to the *visual* entity → "destructible but has no collider or transform;
   it will not break" ×8. A destructible must carry its own collider; `Prop_Crate`'s pivot offset is
   exactly 0, so that is correct placement, not a compromise.

**The measurement — the reason this session mattered.** The town ran at **4.3 fps / 233 ms per
frame**. Isolated it by A/B on the identical scene:

| config | distinct meshes | draws | fps | ms/frame |
|---|---|---|---|---|
| as shipped | 56 | 474 | 4.3 | 233 |
| same 522 entities + same 222 bodies, 1 mesh + 1 material | 1 | 228 | **21.4** | **46.6** |
| no scene | — | — | 75.6 | 13.2 |

**Frame cost scales with the number of DISTINCT MESHES.** Ruled out one variable at a time on the
same scene: shadow cascades (232.8 / 235.0 / 235.7 ms), textures (277 ms — *worse* without), geometry
(only 124,165 triangles), physics (222 bodies present in both rows). The engine's own `perf_gate.sh`
**passes** on this box (3490 draws, 57.1 ms), so the engine is not slow in general. Filed for the
rendering owner in COORDINATION.md with the reproduction, and the rule is now in MEMORY.md: never
quote "the engine handles N entities" without "as M distinct meshes".

**Also learned about the engine's ceiling:** a `.nfscene` can declare only a **directional** light
(the renderer has point shadows but the loader never adds a point light), and a material holds **one**
texture — so the kit's 18 Normal / 9 Roughness / 5 ORM maps are unusable and each `.nfmat` carries
roughness/metallic **scalars** instead. Stated in the project README rather than implied.

**Saved as a skill:** updated `novaforge-build-game` with the kit-import pipeline, the scene-block
grammar trap, the collider/destructible rule, and the distinct-mesh scaling law.
